Backend Architecture

Two drawings. The first is how the pods are arranged and what moves between them; the second is what a single request meets on its way through one process. Both read from the code as it stands — 227 files, 119k lines, 328 HTTP routes.

One image, two roles

The same container runs as the hub and as a per-cluster agent. What differs is a mode flag and which direction the registration goes — so a new managed cluster is a deployment, not a new component.

Why one image

A spoke that drifted from the hub would be a second product to test. Two roles, one binary, one MCP_MODE flag.

Why a heartbeat

It carries the build version and LLM config, so the hub can tell a cluster that is quiet from one running an older image.

Why a proxy, not a copy

Widgets and chat query the spoke live. The cached snapshot exists so the fleet view loads, not so answers go stale.

Inside one process

Two protocols enter, and both land on the same services. That is the claim this drawing exists to make: the MCP tool layer is thin, and nothing in services reaches the network except through a client in utils.

Eleven runtime dependencies

No Express, no ORM, no framework. The HTTP server is Node's own createServer; the rest is the MCP SDK, the Kubernetes client, undici, pg, ioredis, zod, js-yaml and four document libraries.

Per-agent endpoints

A client connecting to /mcp/vm-migration/sse gets a server with only that agent's tools registered. Everything outside the allow-list is not refused at runtime — it was never there.

Why services stays pure

Keeping the network in utils is what lets a scorer be called with a fixture. It is the reason the canaries can check seventeen agents without a cluster.
